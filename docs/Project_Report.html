2. Introduction

Gatehouse is a web-based ERP (Enterprise Resource Planning) system for a housing society. It brings the daily work of a society office – keeping flat and member records, raising monthly maintenance bills, recording payments and handling residents' complaints – into one MySQL database that is used through a web browser.

The system has two kinds of users. The admin (society office) manages all records and sees reports. Every flat gets its own login ID (the flat number, for example A-101) and password, so residents can check their bills and dues and raise complaints online without visiting the office.

The application is built with HTML, CSS and JavaScript on the front end, PHP on the server and MySQL as the database, and runs on the XAMPP server. The sample data describes a society called Palm Grove Residency with 24 flats in three blocks (A, B and C), 27 residents, 60 maintenance bills for September–November 2026 and 11 complaints.

3. Problem Definition

Most small and medium housing societies still run on paper registers, receipt books, spreadsheets and WhatsApp groups. This causes the following problems:

  • Scattered records – flat details, member lists and payment receipts are kept in different registers, so finding one flat's full history takes time.
  • Untracked dues – the office has no quick way to see which flats have not paid maintenance, for how many months, and the total amount pending.
  • Manual billing – the bill for every flat has to be written or typed again every month, which is slow and error-prone.
  • Lost complaints – complaints given verbally or on WhatsApp are forgotten; residents cannot see whether anyone is working on them.
  • No self-service – residents must visit or call the office to know their dues or the status of their complaint.
  • No reports – preparing a defaulter list or a month-wise collection summary for the committee meeting is done by hand.

Gatehouse solves these problems with a single database-driven system that the office and the residents both use.

4. Objectives

  1. To store flats, residents, maintenance bills and complaints in a relational MySQL database with proper primary and foreign keys.
  2. To provide complete Create, Read, Update and Delete (CRUD) operations for every main module.
  3. To provide search and filter options on every list (by flat number, name, block, type, status, month and category).
  4. To generate the monthly maintenance bill for all occupied flats with a single click, using a fixed rate per flat type.
  5. To give every flat its own secure login so residents can view their bills and dues and raise and track complaints.
  6. To validate every form both in the browser (JavaScript) and on the server (PHP).
  7. To produce reports on unpaid maintenance, month-wise collection and complaints.
  8. To keep the system secure using password hashing, prepared statements and role-based access.

9. Module Description

9.1 Login Module

The login page (index.php) has two tabs. Admins log in with a username; residents log in with their flat ID. The typed password is checked with password_verify() against the stored hash. On success the user's ID is stored in the PHP session and the right dashboard opens. Every admin page calls require_admin() and every resident page calls require_resident(), which send an unauthorised user back to the login page.

// admin/flat_add.php
[$d, $errors] = validate_flat(true);              // server-side validation
if (!$errors) {
    $hash = password_hash($d['password'], PASSWORD_DEFAULT);
    db_execute($conn,
        "INSERT INTO flats (flat_no, password, block, floor_no,
                            flat_type, area_sqft, status)
         VALUES (?, ?, ?, ?, ?, ?, ?)",
        'sssisis',
        [$d['flat_no'], $hash, $d['block'], $d['floor_no'],

}

12.1 Security checks

  • SQL injection – all queries use prepared statements; input like ' OR '1'='1 in the search box is treated as plain text.
  • XSS – every value printed on a page passes through htmlspecialchars().
  • Passwords – stored as bcrypt hashes; the database never holds a readable password.
  • Access control – a resident's queries always include flat_id = ? taken from the session, never from the form.

13. Conclusion

Gatehouse meets all the requirements of the ERP-based CRUD mini project. It solves a real management problem – running a housing society – with a database-driven web application built on HTML, CSS, JavaScript, PHP and MySQL.

The system implements complete Create, Read, Update, Delete and Search operations in four modules (Flats, Residents, Maintenance Bills and Complaints), validates every form in the browser and on the server, and provides a dashboard and reports. Separate logins for the society office and for each flat make it useful for both the management and the residents. While building it, the group gained practical experience in database design with keys and relationships, server-side programming with PHP sessions and prepared statements, and testing a complete application.
